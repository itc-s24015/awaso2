# アカウント・関連データ削除

## 詳細
初版で利用者がアカウント削除を実行できるようにする。本人のアカウントとプロフィール、本人が作成した企画、投稿した写真、企画に紐づく本人の回答を削除する。

## 仕様
### 処理の流れ
1. 利用者がGoogle OAuthで再認証し、削除対象の説明を確認したうえで削除を確定する。
2. システムが永続化された削除ジョブを作成し、プロフィールを`deletion_pending`にしてアプリとStorageのRLSアクセスを遮断する。対象Storageオブジェクトの一覧をジョブ項目として保存する。
3. システムがSupabase Storage APIで対象ファイルを削除し、項目ごとに成功・失敗状態を記録する。失敗時はジョブ段階を保持して再試行し、完了を表示しない。
4. Storage削除完了後、1つのDBトランザクションで本人が作成した企画、投稿した写真ファイル、企画に紐づく本人の回答、参加申請、グループメンバーシップ、通知設定・Push送信先・本人宛て送信記録を削除する。本人が作成した企画以外の共有レコードは維持し、作者参照をNULLにする。本人が別の利用者の企画に投稿した写真はファイルを削除し、説明文があれば作者参照をNULLにして文章を残す。管理者である各グループについては、他のメンバーがいれば在籍期間が最も長いメンバーに管理者を移譲し、同時刻ならユーザーID昇順で決定する。ほかのメンバーがいなければグループと関連データを削除する。
5. DBトランザクション完了後、サーバーからSupabase Authの管理APIでユーザーを削除する。成功後に削除完了を表示する。

### 入出力
- 入力：認証済み利用者の削除要求と確認操作。
- 出力：`削除中`、`再試行が必要`、`完了`の状態。すべての段階が完了した場合のみ`完了`を表示する。途中失敗時は、処理が継続中であることと再試行・問い合わせ方法を案内する。

### 制御・安全性
- 削除操作は対象の利用者本人が認証された状態で実行する。
- 削除ジョブはGoogle OAuth再認証直後のセッションと明示的な最終確認が揃った場合のみ作成する。対象ユーザーIDはクライアント入力ではなく、検証済みセッションから取得する。
- 作成した企画を削除することで、他メンバーの回答や企画写真も削除対象となることを事前に明示する。
- StorageオブジェクトはSupabase Storage APIで削除し、`storage.objects`へのSQL削除を行わない。
- Auth削除前にプロフィールを`deletion_pending`とし、発行済みJWTが有効な間もRLSでアクセスを拒否する。
- ジョブ・オブジェクト項目はサービスロールを使うサーバー側だけが操作できる。秘密鍵をクライアントへ公開しない。
- 既存のStorageオブジェクトを含めて削除対象を列挙し、オブジェクト単位で進捗を記録して再試行できるようにする。アカウント所有の全ファイル、削除対象企画・グループに含まれるファイルを対象とする。Storage APIでユーザーIDを含むパスを列挙し、削除対象を確定する。
